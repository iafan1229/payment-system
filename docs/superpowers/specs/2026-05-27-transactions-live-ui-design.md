# 트랜잭션 라이브 UI/UX 설계

**날짜:** 2026-05-27  
**범위:** `transactions` 목록/상세 화면의 실시간 UX, `sandbox` / `production` 시각 분리, 환경 전환 처리, `production` 확인 UI, Tailwind 기준 스타일 설계

## 배경

현재 앱은 이미 다음 구조를 가지고 있다.

- 환경 상태는 URL의 `?env=`와 `localStorage`로 관리한다.
- 트랜잭션 데이터는 React Query polling으로 갱신한다.
- 인증 상태만 Zustand에 저장한다.
- 거래 목록과 상세 화면은 `app/(protected)/transactions` 아래에서 동작한다.

이번 설계의 목적은 기존 정보 구조를 유지하면서도, 다음 네 가지 상황에서 UI/UX를 더 명확하게 만드는 것이다.

1. 환경 전환 시 페이지 처리, 특히 상세 화면 처리
2. `production` 전환 시 확인 여부 UI
3. 실시간으로 들어오는 새 트랜잭션 노출 방식
4. 상세 페이지를 보던 중 해당 트랜잭션이 갱신될 때의 반영 방식

## 우선순위

사용자와 합의한 우선순위는 아래와 같다.

1. **실시간 가시성**
2. **읽기 연속성**
3. **운영 안전성**

즉, 새 거래와 상태 변화를 놓치지 않게 보여주는 것이 가장 중요하고, 그 다음으로 사용자가 읽던 맥락을 지켜야 한다. 운영 안전성은 특히 `production` 진입과 환경 전환 처리에서 보완한다.

## 이번 범위에서 유지하는 원칙

- 환경의 기준 상태는 계속 **URL**로 둔다.
- `localStorage`는 마지막 환경 복원용으로만 쓴다.
- 이번 범위에서는 **Zustand를 추가 사용하지 않는다**.
- 서버 데이터는 계속 **React Query**가 소유한다.
- 실시간 UI는 **페이지 로컬 상태 + 직전 응답 비교**로 처리한다.
- 상세 화면에는 환경 전환 스위처를 직접 두지 않는다.
- 디자인은 **Tailwind 기준**으로 정의하고, 구현 단계에서는 Tailwind를 도입해 거래 화면부터 적용한다.

## 선택한 방향

세 가지 방향 중 다음 조합을 채택한다.

- 기본 구조는 **Live Desk형**
- 안전장치는 **Alert First형의 일부만 선택**

의미는 다음과 같다.

- 목록과 상세의 기존 구조는 유지한다.
- 실시간 변화는 적극적으로 노출한다.
- 다만 `production` 전환과 상세 본문 갱신은 즉시 덮어쓰기보다 한 단계 제어된 UI를 둔다.

이 방향은 현재 우선순위인 “실시간 가시성 > 읽기 연속성 > 운영 안전성”과 가장 잘 맞는다.

## 현재 제약과 설계에 반영한 결정

### 1. Tailwind가 아직 설치되어 있지 않음

`package.json` 기준 현재 앱에는 Tailwind 의존성이 없다.  
이번 설계에서는 사용자가 Tailwind 기반 사고를 원했으므로, 구현 단계에서는 **Tailwind를 도입하고 거래 화면부터 우선 적용한다**.

구체적 기준:

- 거래 목록/상세 화면은 Tailwind로 구현한다.
- 기존 전역 CSS는 로그인, 공통 셸 등 아직 이전하지 않은 화면을 위해 당분간 유지한다.
- 이번 작업의 목적은 앱 전체 재스타일링이 아니라 `transactions` 화면군의 라이브 UX 개선이다.

### 2. 상세 API에는 `updated_at`이 없음

현재 상세 타입에는 `status`, `events`, `metadata`, `payment_method`는 있지만 `updated_at`은 없다.  
따라서 상세 화면의 실시간 변화는 “업데이트 시각”이 아니라 **필드 diff**로 판단한다.

### 3. 기존 상세 polling 정책은 `pending`일 때만 동작함

현재 구현은 `pending` 상태일 때만 상세를 재조회한다.  
하지만 이번 우선순위는 실시간 가시성 우선이므로, 상세 화면에서는 **화면이 열려 있는 동안 5초 polling 유지**를 새 기준으로 잡는다.

이 결정으로 얻는 장점:

- 사용자가 상세를 읽는 동안 상태 변화와 이벤트 추가를 놓치지 않는다.
- “상세를 보던 중 업데이트” UX를 실제로 성립시킬 수 있다.

이 결정으로 생기는 비용:

- 기존보다 상세 API 호출 수가 늘어난다.

이번 범위에서는 한 번에 한 거래만 여는 사용 패턴을 전제로, 가시성 이점을 더 크게 본다.

## 환경별 시각 시스템

핵심 규칙은 다음이다.

- 정보 구조는 같게 유지한다.
- 첫인상, 경고 밀도, 하이라이트 톤을 환경별로 분리한다.
- 사용자는 리스트에 들어온 즉시 현재 환경을 인지할 수 있어야 한다.

### 공통 규칙

- 페이지 최상위 래퍼에 `data-env="sandbox|production"`를 둔다.
- 개별 컴포넌트를 환경별로 두 벌 만들지 않는다.
- `data-[env=sandbox]:...`, `data-[env=production]:...` 식의 variant로 톤을 나눈다.

### Sandbox 시각 톤

`sandbox`는 “실험적이고 빠르게 읽히는 연습장 피드”로 보이게 한다.

- 배경: 따뜻한 샌드/앰버 기반의 밝은 그라데이션
- 카드 표면: 반투명 화이트
- 보더: 연한 앰버
- 새 거래 하이라이트: 골드/앰버 계열
- 상태 변경 플래시: 따뜻한 틴트
- 분위기: 흐름이 활발하고, 새 입력이 적극적으로 드러남

권장 Tailwind 톤:

- 페이지 배경: `bg-[radial-gradient(circle_at_top,_rgba(245,158,11,0.16),transparent_32%),linear-gradient(180deg,#fffaf0_0%,#f8eddc_100%)]`
- 컨텍스트 스트립: `border-amber-300/40 bg-amber-100/70 text-amber-950`
- 테이블 카드: `border-amber-200/60 bg-white/80`
- 새 거래 row: `bg-amber-100/70 ring-1 ring-amber-300`
- 상태 변경 row/cell: `bg-amber-50`

### Production 시각 톤

`production`은 “절제된 운영 콘솔”로 보이게 한다.

- 배경: 옅은 슬레이트/아이보리 잉크톤
- 카드 표면: 불투명도 높은 화이트
- 보더: 선명한 슬레이트 그레이
- 상단 컨텍스트 스트립: 짙은 잉크 바탕
- 새 거래 하이라이트: 절제된 시안/민트 계열
- hover와 애니메이션: `sandbox`보다 절제
- 분위기: 실거래를 보고 있다는 인지가 즉시 와야 함

권장 Tailwind 톤:

- 페이지 배경: `bg-[linear-gradient(180deg,#f8fafc_0%,#eef2f7_100%)]`
- 컨텍스트 스트립: `border-slate-300/70 bg-slate-900 text-slate-50`
- 테이블 카드: `border-slate-300/70 bg-white/92`
- 새 거래 row: `bg-cyan-50 ring-1 ring-cyan-300`
- 상태 변경 row/cell: `bg-slate-50`

## 환경 전환 UX

### 기준 동작

- `sandbox -> production` 전환 시에만 확인 UI를 띄운다.
- `production -> sandbox` 전환은 즉시 수행한다.
- 전환 후 환경 값은 URL `?env=`에 기록한다.

### 왜 한쪽 방향만 확인하는가

이번 범위에서 위험한 방향은 “실수로 실거래 환경으로 들어가는 것”이다.  
반대로 `production -> sandbox`는 위험보다 안전 쪽으로 이동하는 흐름이므로, 추가 확인으로 속도를 늦출 필요가 없다.

### 상세 화면에서 환경이 바뀌는 경우

상세 화면은 환경 전환 스위처를 직접 갖지 않는다.  
하지만 아래 경우는 처리해야 한다.

- 사용자가 앞으로 전역 헤더에서 환경을 바꾼다.
- 사용자가 URL을 직접 수정한다.
- 링크 이동으로 다른 환경이 들어온다.

이때의 기준은 다음과 같다.

- 현재 경로가 `/transactions/[id]`이면, 목표 환경의 **목록 페이지**로 이동시킨다.
- 즉, `/transactions/[id]?env=sandbox` 에서 `production`으로 바꾸면 `/transactions?env=production` 으로 이동한다.

이 결정을 택한 이유:

- 같은 `id`가 두 환경에서 같은 의미라는 보장이 없다.
- 상세 화면은 읽기 컨텍스트가 강하므로, 환경 전환 시 동일 상세를 억지로 덮어쓰는 것이 더 혼란스럽다.

## Production 전환 확인 UI

### 형태

`production` 전환 확인 UI는 가운데 모달이 아니라 **우측 상단 anchored panel**로 둔다.

이 형태를 택하는 이유:

- 화면을 완전히 가리지 않는다.
- 환경 스위처와 인접해 인과관계가 명확하다.
- “전역 문맥 전환”이라는 느낌을 유지할 수 있다.

### 구조

- 제목
- 짧은 설명
- 취소 버튼
- 계속 버튼

### 권장 문구

- 제목: `Production 거래를 보시겠습니까?`
- 설명: `실시간 실거래 상태가 표시되며, 상세 화면을 보고 있었다면 목록으로 이동합니다.`

### Tailwind 기준

- 패널: `absolute right-0 top-[calc(100%+12px)] w-[320px] rounded-3xl border border-slate-300 bg-white p-5 shadow-2xl`
- 제목: `text-base font-semibold text-slate-950`
- 설명: `mt-2 text-sm leading-6 text-slate-600`
- 취소 버튼: `rounded-full border border-slate-300 bg-white px-4 py-2`
- 계속 버튼: `rounded-full bg-slate-950 px-4 py-2 text-white`

### 상호작용

- 취소 시 패널만 닫고 현재 환경 유지
- 계속 시 URL 갱신 후 대상 화면 이동
- 열렸을 때 첫 포커스는 **취소 버튼**에 두고, `Esc`로 닫을 수 있어야 한다

## 목록 화면 라이브 UX

### 기본 원칙

- 새 거래는 “놓치면 안 되는 신호”처럼 보여야 한다.
- 상태 변경은 “이미 보던 항목의 업데이트”처럼 보여야 한다.
- 사용자가 아래를 읽는 중이면, 자동 삽입보다 읽기 맥락을 우선한다.

### 라이브 상태 바

헤더 아래에 얇은 `live bar`를 둔다.

표시 정보:

- 마지막 동기화 시각
- 새 거래 수
- 상태 변경 수

역할:

- 사용자가 polling이 살아 있다는 사실을 즉시 이해하게 한다.
- “무엇이 바뀌었는지”를 테이블까지 내려가지 않고 먼저 요약해 준다.

권장 Tailwind 기준:

- `sticky top-3 z-20 flex items-center gap-3 rounded-full px-4 py-2 backdrop-blur`

### 목록 상단 근처에 있을 때

사용자가 목록 상단 근처에 있을 때는 새 거래를 즉시 삽입한다.

판정 기준:

- viewport 기준 상단에서 160px 이내
- 또는 테이블 헤더가 거의 보이는 상태

즉시 삽입 시 UI:

- 새 row를 테이블 맨 위에 삽입
- 3~4초 동안 환경별 하이라이트 적용
- row 왼쪽에 2px accent bar 표시
- 진입 모션은 짧은 `opacity + translate-y`로 제한

### 아래로 스크롤한 상태일 때

사용자가 아래를 읽고 있으면 새 row를 즉시 밀어 넣지 않는다.

대신:

- 새 거래를 로컬 큐에 쌓는다.
- 상단에 `새 거래 3건 보기` 배너를 띄운다.
- 사용자가 배너를 누르면 그때 한 번에 반영한다.
- 반영 시 현재 스크롤 점프를 강제하지 않는다.

이 동작은 실시간 가시성과 읽기 연속성의 균형점이다.

### 기존 row의 상태가 바뀔 때

상태 변경은 새 거래와 다른 방식으로 보여준다.

- row 전체를 과하게 번쩍이지 않는다.
- 우선 `status pill`을 강조한다.
- 필요하면 amount/refund 관련 셀만 보조 하이라이트한다.
- row 왼쪽 accent는 짧게 나타났다가 사라진다.

사용자는 “새 항목이 생겼다”와 “기존 항목이 바뀌었다”를 한눈에 구분할 수 있어야 한다.

### 빈 상태

빈 상태도 환경별 컨텍스트를 유지한다.

- `sandbox`: “새 거래가 생성되면 자동으로 이 목록에 반영됩니다”
- `production`: “실거래가 들어오면 자동으로 이 목록에 반영됩니다”

문구 차이는 작지만, 현재 보고 있는 환경의 성격을 다시 한 번 상기시킨다.

## 상세 화면 라이브 UX

### 핵심 원칙

- 핵심 상태는 바로 따라간다.
- 읽고 있는 본문은 사용자가 승인하기 전까지 함부로 덮어쓰지 않는다.

### 즉시 반영과 적용 대기의 구분

즉시 반영 대상:

- `status`
- 새 `event` 추가
- 금액/통화처럼 식별성이 강한 핵심 정보

적용 대기 대상:

- `metadata`
- `payment_method`

이렇게 나누는 이유:

- 상태와 타임라인은 “흐름” 자체라서 늦게 반영하면 실시간성이 무너진다.
- 메타데이터와 결제수단 정보는 사용자가 본문을 읽는 중일 수 있으므로, 갑자기 덮어쓰면 읽기 연속성이 크게 깨진다.

### 상단 라이브 업데이트 바

상세 화면 상단에는 얇은 업데이트 바를 둔다.

가능한 메시지 예시:

- `상태가 succeeded로 변경됨`
- `이벤트 1건 추가됨`
- `메타데이터 변경 2건 적용`

역할:

- 즉시 반영된 변화와 적용 대기 변화를 한 곳에서 안내한다.
- 본문을 읽다가도 변화가 생겼다는 사실을 놓치지 않게 한다.

권장 Tailwind 기준:

- `sticky top-3 z-20 flex items-center justify-between rounded-2xl border px-4 py-3 backdrop-blur`

### 본문 카드 하이라이트

전체 페이지를 다시 칠하지 않고, 바뀐 카드만 짧게 표시한다.

- summary 카드: 상단 border 또는 status 영역만 강조
- timeline 카드: 새 이벤트 행만 강조
- metadata 카드: 사용자가 적용 버튼을 누른 후 해당 항목만 강조
- payment method 카드: 적용 후 카드 헤더만 한 번 강조

### polling 기준

상세 화면은 **화면이 열려 있는 동안 5초 polling**을 유지한다.

추가 조건:

- 백그라운드 탭에서는 `refetchIntervalInBackground=false`로 둔다
- 탭이 다시 foreground로 돌아오면 즉시 1회 재조회한다

이번 설계에서 상세 polling을 유지하는 이유는 “상세를 보고 있는 중 업데이트됨” 요구를 실제 UX로 연결하기 위해서다.

## 로컬 상태 구조

이번 범위에서는 전역 store를 추가하지 않는다.

### 목록 페이지 로컬 상태

- `isNearTop`
- `queuedNewRows`
- `freshRowIds`
- `changedRowIds`
- `showProductionConfirm`

### 상세 페이지 로컬 상태

- `pendingDetailPatch`
- `pendingFieldKeys`
- `showUpdateBar`

### 왜 로컬 상태로 충분한가

- 새 거래 배너와 상세 적용 대기는 화면 단위 맥락이다.
- 라우트를 건너 여러 화면이 동시에 공유할 필요가 없다.
- React Query가 이미 서버 데이터 원본을 관리한다.

즉, 이번 범위의 상태는 “전역 데이터”가 아니라 “현재 화면 반응”에 가깝다.

## 데이터 diff 규칙

### 목록 화면

목록은 이전 polling 결과와 새 결과를 비교해 다음을 계산한다.

- 새 응답에만 있고 이전 응답에는 없는 `id` -> 새 거래
- 같은 `id`인데 `status`가 달라짐 -> 상태 변경

이 비교 결과를 바탕으로:

- 새 거래는 즉시 삽입 또는 큐 적재
- 상태 변경은 대상 row/cell 하이라이트

### 상세 화면

상세는 이전 응답과 새 응답을 비교해 다음을 계산한다.

- `status` 변경 여부
- `events.length` 증가 여부
- `metadata` shallow diff
- `payment_method` shallow diff
- 금액/통화 diff

`updated_at`이 없으므로, 이 비교 규칙을 명시적으로 코드화해야 한다.

## 로딩, 오류, 접근성

### 로딩

- 목록 초기 진입 로딩은 현재 카드형 피드백을 유지한다.
- 이후 background polling은 전체 skeleton으로 바꾸지 않고, `live bar`와 작은 활동 표시로만 드러낸다.
- 상세도 최초 로딩만 전체 로딩 카드를 쓰고, 이후 재조회는 업데이트 바와 부분 하이라이트로 표현한다.

### 오류

- 목록 polling 중 오류가 나도 기존 목록은 유지한다.
- `live bar` 근처에 마지막 갱신 실패를 짧게 표시한다.
- 상세도 이전 성공 데이터가 있으면 화면은 유지하고, 갱신 실패 안내만 상단에 추가한다.

### 접근성

- 새 거래 수와 업데이트 알림은 `aria-live="polite"`로 읽히게 한다.
- `production` 확인 패널은 키보드로 완전 조작 가능해야 한다.
- motion 축소 환경에서는 위치 이동 애니메이션을 끄고 색상 강조만 남긴다.
- 색상만으로 상태를 구분하지 않도록 텍스트 레이블을 유지한다.

## 이번 범위에서 하지 않는 것

- 새 전역 라이브 센터 구축
- WebSocket 또는 SSE 도입
- 상세 화면 내부 환경 전환 스위처 추가
- `sandbox`와 `production`을 완전히 다른 레이아웃으로 분리
- Zustand 기반 라이브 이벤트 저장소 도입

## 테스트 전략

### 단위 테스트

- 목록 diff 함수가 새 거래와 상태 변경을 정확히 분류하는지 검증
- 상세 diff 함수가 즉시 반영 필드와 적용 대기 필드를 정확히 나누는지 검증
- 환경 전환 로직이 상세 경로에서 목록 경로로 안전하게 바뀌는지 검증

### 컴포넌트 테스트

- 목록 상단 근처일 때 새 row가 즉시 삽입되는지 확인
- 아래로 스크롤한 상태일 때 배너만 표시되는지 확인
- `sandbox -> production`에서 확인 패널이 열리고, 취소/계속이 올바르게 동작하는지 확인
- 상세에서 metadata 변경이 바로 렌더링되지 않고 “적용” 액션을 기다리는지 확인

### 수동 QA

- `sandbox`와 `production` 첫인상이 충분히 다르게 느껴지는지 확인
- 새 거래가 빠르게 들어오는 상황에서도 사용자가 현재 읽던 row를 잃지 않는지 확인
- 상세에서 상태 변경과 메타데이터 변경이 서로 다른 방식으로 읽히는지 확인
- 모바일 폭에서 sticky 배너와 업데이트 바가 과도하게 공간을 차지하지 않는지 확인

## 구현 단계로 넘길 핵심 결정 요약

- 환경 상태는 계속 URL 기준으로 유지한다.
- `production` 진입만 확인 패널을 둔다.
- 상세에서 환경이 바뀌면 대상 환경의 목록으로 이동한다.
- 목록은 “상단 근처면 즉시 삽입, 아래에 있으면 배너 큐” 모델을 쓴다.
- 상세는 “핵심 상태 즉시 반영, 본문 정보는 적용 대기” 모델을 쓴다.
- Zustand는 쓰지 않는다.
- Tailwind를 도입해 거래 화면부터 적용한다.
