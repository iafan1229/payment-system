# Hopae Software Engineer

## 배경

당신은 결제 플랫폼의 어드민 대시보드를 만드는 엔지니어입니다. 가맹점이 자사의 결제 내역을 확인하는 화면 일부를 구현합니다.
핵심 요구사항은 두 가지입니다:

1. **Sandbox / Production 환경 간 전환**
2. **트랜잭션 목록의 준실시간 (near real-time) 갱신** mock 서버에서 새 트랜잭션가
   들어오고 `pending` 트랜잭션가 `succeeded`/`failed`로 전이됩니다. 사용자가 화면을
   보고 있을 때 그 변화가 합리적인 시간 안에 (수십 초 이내) 반영되어야 합니다.
   구체적인 방식은 본인 선택.

## 기술 스택

- **React + TypeScript**, 또는 **Next.js (App Router 권장)**
- 그 외 라이브러리 (상태 관리, 데이터 페칭, 스타일링) 는 자유
- 단, 선택한 이유는 README에 한 줄씩이라도 기록해주세요

## 구현할 화면

### 1. 로그인

- 이메일 + 비밀번호 폼
- `POST /api/auth/login` 호출
- 성공 시 토큰 저장 후 대시보드로 이동
- 실패 시 사용자에게 명확한 피드백

테스트 계정: `demo@hopae.com / password123`

### 2. 대시보드 트랜잭션 목록

- **Sandbox ↔ Production 환경 스위처 노출**
- 트랜잭션 목록 (ID, 금액, 통화, 상태, 고객명, 생성일)
- 환경 전환 시 데이터가 그에 맞게 갱신
- **준실시간 갱신**:
  - mock 서버의 데이터는 시간이 지나면서 변합니다 새 트랜잭션가 추가되고
    `pending` 트랜잭션의 상태가 바뀝니다 (자세한 동작은 `mock-server/README.md` 참고)
  - 사용자가 목록을 보고 있을 때 이런 변화가 반영되어야 합니다
  - 동기화 방식과 UI 노출은 본인 선택. 필요하다면 mock 서버를 수정해도 됩니다.
- 행 클릭 → 상세 페이지

### 3. 트랜잭션 상세

- 트랜잭션 기본 정보 (금액, 상태, 시각, ID)
- 고객 정보
- 결제 수단
- 이벤트 타임라인 (`created` → `authorized` → `captured` 등)
- **상세 페이지 표시 중 해당 트랜잭션가 갱신되면** 어떻게 처리할지도 본인 결정
- 목록으로 돌아가기

## 제공 API

Base URL: `http://localhost:4000`. mock 서버를 함께 제공합니다 (`mock-server/`).

```
POST /api/auth/login
GET  /api/transactions?env=sandbox|production&limit=&cursor=
GET  /api/transactions/:id           (X-Environment 헤더)
```

mock 서버는 백그라운드에서 데이터를 변화시킵니다 자세한 동작은
`mock-server/README.md` 참고.

## ⚠️ API 명세는 가이드라인입니다

이 API는 의도적으로 미완성/비일관적이거나 개선의 여지가 있을 수 있습니다.

- 본인이 더 나은 설계가 있다고 판단하면 **API 형태를 변경하거나 새로 정의해도
  좋습니다.** mock 서버 코드도 자유롭게 수정 가능합니다.
- 명세를 그대로 따랐든 바꿨든, **그 판단의 근거를 README에 적어주세요.**

## 제출물

GitHub 저장소 (공개 또는 초대) 로 제출. README에 다음을 포함해주세요:

1. **실행 방법** (앱 + mock 서버)
2. **사용한 주요 라이브러리와 선택 이유** 특히 다음 두 가지는 명시:
   - 환경 (env) 상태를 어디에 저장하는지 (URL? Context? store?) 와 그 이유
   - 준실시간 갱신을 어떻게 구현했는지와 왜 그 방식을 골랐는지
3. **API 명세에서 발견한 문제점 또는 개선 제안** (없다면 "없음"으로 적어도 됨)
4. **명세에 없어서 본인이 결정한 사항과 그 이유**
   예시:
   - 환경 전환 시 페이지 (특히 상세 화면) 처리
   - 새로고침 시 환경 유지
   - 토큰 만료 처리
   - Production 전환 시 확인 (confirmation) 여부
   - 실시간으로 들어오는 새 트랜잭션를 UI에 어떻게 노출할지
   - 상세 페이지를 보던 중 해당 트랜잭션가 업데이트되면
5. **시간이 더 있었다면 추가/개선하고 싶은 것**
6. **의도적으로 단순화하거나 생략한 부분** (있다면)

## 평가 기준

- **코드 품질** 구조, 가독성, 타입 안전성, 컴포넌트 분리
- **상태 관리 설계** 인증, 환경 (env), 실시간 데이터의 캐시 머지
- **기술사용의 정확성** hooks, 데이터 페칭, 캐싱, 리렌더 관리
- **UX 디테일** 로딩/에러/빈 상태, 환경 전환의 시각적 구분, 실시간 업데이트의
  UX (사용자 흐름을 방해하지 않으면서도 변화를 드러내는 방식)
- **README의 깊이** 위 3, 4, 5번에서 후보자의 사고 과정을 봅니다. **이 부분이
  가장 중요합니다.**
